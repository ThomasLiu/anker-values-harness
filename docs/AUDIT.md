# 评测方法学：第一轮新实验前必须补齐的洞

> 这份文档按 harness 自己的格式写，并且必须通过 `vh lint pre_deliver`。
> 基准取自 Anthropic《Demystifying evals for AI agents》的六组件定义，
> 加上 lm-evaluation-harness 与 Inspect 的工程实践。

## 真实目标

**表面需求**：给重建后的基准配一套评测方法。

**真实目标**：让第一轮新实验产出的数字，第一次就是**可引用、可复现、可比较**的。
判断标准不是"数字好看"，而是——三个月后有人问「这个分数是怎么测出来的」，
能拿出一条命令跑出同样的结论，或者明确指出当时的方法缺陷在哪。

**依据**：telemetry 里没有 trial 概念——同一份产出失败 6 次再通过，会贡献 5 个失败样本，
通过率被返工次数污染；critic 分数从来没进过归档，评分只活在对话里；grader 从没被校准，
没人知道 0-3 分的边界靠不靠谱。这三条不修，跑多少轮实验都产不出可引用的结论。

## 分工边界

并行会话正在做**内容层**重建：`bench/`、`scenarios/`、`gates/`、`rubrics/`、
`README.md`、`VALUES.md`、CI 配置。这份方案只碰**方法层**：`vhcore/telemetry.py`、
`vhcore/cli.py`、本文件。两边不交叉，改动可以独立回滚。

## 关键假设

- 假设：新 bench 的 17 个用例足以支撑第一轮实验 → 验证：三阶段各跑一轮，若某阶段可用用例 <3 条则判为不足，需要补
- 假设：`cg.tradeoff-declared` 缺反例是遗漏，不是有意省略 → 验证：查 `cases.toml` 注释与 git log，确认无"该规则暂不验证"的论证
- 假设：重建后的场景与 `values.toml` 的规则语义仍然对齐 → 验证：对 6 份正例跑 lint，skipped 总数 ≤1 即对齐（实测：1 份 1 条，`cg.tradeoff-declared`）
- 假设：旧实验的方向性结论（求极致提升最大）在新场景下仍然成立 → 验证：新实验跑完，若求极致仍为三项中提升最大则成立，否则说明该结论依赖旧场景

## 验收标准

- G1 14 条规则里，每条 blocking 规则都有 ≥1 个反例；当前 10/10 覆盖，缺 `cg.tradeoff-declared`
- G2 每条 telemetry 记录含 `trial` 与 `skipped` 字段，`trial` 从 1 连续递增
- G3 `vh report` 同时输出首次通过率、最终通过率、返工份数三个口径
- G4 `vh report --export` 默认剔除临时目录记录，归档文件零条 `/tmp`
- G5 critic 校准记录存在，含同一产出的多次评分极差与命中率　**← 已达成：v1 判死（命中 50%、区分度 0），v2.1 通过（命中 100%、区分度满）**
- G6 `vh selftest` 16/16 保持通过，且新增反例不破坏现有用例（现为 17/17）
- G7 第一轮新实验三阶段全跑，`post_task` 记录数 ≥6　**← 已达成，实测 12 条**

## 方案

### A1 · trial 语义与三口径报告（已完成）

**问题**：`report()` 的分母是 lint 次数。一份文件失败 6 次再通过，会贡献 5 个失败
样本，把通过率压掉十几个点——而被压掉的那部分衡量的是返工，不是能力。

**已改**：`vhcore/telemetry.py`

- `record()` 新增 `trial`（同阶段同产出的第几次）与 `skipped`（没触发的规则）
- 新增 `_final_by_artifact()`：按 `(阶段, 产出)` 取最后一次，算最终合格率
- 新增首次通过率：`trial=1` 那次的通过情况

**为什么三个口径都要留**：

| 口径 | 回答的问题 |
|---|---|
| 首次通过率 | 一次做对的能力（对应 pass@1） |
| 最终通过率 | 交付合不合格（对应 pass^k，在"都修到过"的实验里恒为 100%） |
| 返工份数 | 返工有多磨——这是 harness 最主要的副作用指标 |

只留一个，另外两个问题就变成盲区。最终通过率在「所有产出都被修到过」的实验里恒为
100%，**这个口径单独用会误导，必须三个一起看**。

### A2 · 归档过滤（已完成）

**问题**：`export()` 是裸 `shutil.copyfile`，把 `/tmp/t1.md`、`/tmp/tB.md` 这些探针

`/temp/` 前缀的记录。CLI 增加 `--all` 开关。

### B2 · 跑第一轮新实验（已完成，结论：这轮没测出效果，但测出了尺子坏了）

**问题**：重建后 telemetry 归零，三阶段里只跑过前两段，共成长维度没有任何记录。

**已做**：4 场景（研发 / 非研发各 2）× 3 条件（BASE / OPEN / BLIND）× 3 阶段，
共 12 个 run、36 份产出、28 条 lint、36 条 critic 评分。归档在 `eval/telemetry/r3.jsonl`，
产出在 `eval/r3/runs/`，完整记录见 `eval/RESULTS.md`，统计用 `python eval/r3/score.py`。

实验目录放在仓库外（`/Users/thomas/Projects/vh-r3-lab/`）而不是 `eval/r3/runs/`。
第一版放在仓库内，BASE 组的产出里直接出现了「红队自查 / 影响范围 / 取舍声明 / 技术债」——
裸跑 agent 不会自发写出 harness 的必答段名，它去翻了仓库。搬出去并明令禁止后归零。

**结果一：门禁几乎不区分。** 24 份带门禁的产出里 23 份第一次 lint 就通过，
唯一一次返工是标题写法没被识别为段落。14 条规则里 9 条零失败。规则一旦写进 prompt，
agent 几乎不会违反——门禁把「按要求写」和「没按要求写」分开，而后者在这轮几乎不存在。

**结果二：critic 打不出区分。** BASE 组 12 份产出拿到 **12 个完全相同的 2/2/2**，
标准差 0.00。同样是 2/2/2，verdict 却有 9 份「可交付」、3 份「需返工」——
同一个分数推出不同结论，分数和结论已经脱钩。三个维度上，32/36、30/36、29/36 都落在 2 分。
`critic.md` 写「默认往低打」，实际行为是「默认给 2 分」，因为 2 分（合格：有实质内容但存在
可改进空隙）这个描述几乎无法被证伪。

**结果三：上一轮的核心叙事不成立。** 求极致 BASE 2.00 → BLIND 2.08（+0.08），
上一轮是 0.25 → 3.00（+2.75）。方向一致但幅度差一个数量级，而 0.08 在 n=4 的噪声范围内。
README 里「求极致从 0.25 涨到 3.00 是最大贡献」在新数据下没有支撑。

**验收**：G7 达成（`post_task` 记录 12 条，上一轮 0 条）。
`vh report --from eval/telemetry/r3.jsonl` 可复现全部过程指标，
`python eval/r3/score.py` 可复现全部结果指标。

**没达成的**：这轮回答不了「harness 有没有用」。不是 harness 没用，是量它的尺子坏了。
在 B3 通过之前，任何基于这轮 critic 分数的结论都不能引用。

**已知缺陷**：每格 n=4、单 trial；BASE 组仍拿到「三份文档」的结构提示，不是真空白基线；
BLIND 的隔离靠指令不靠沙箱。三条都写进了 `eval/RESULTS.md` 的技术债。

### B3 · critic 校准（已完成：v1 判死，v2.1 通过）

**问题**：critic 的 0-3 分档边界是自己划的，没有金标准、没有一致性检验。分数不能被
引用，根本原因是**没人知道这个打分器本身靠不靠谱**。

**已做**：12 份金标准（`bench/positive` 6 份 + `bench/negative` 6 份），单次盲评 12 次，
另选 4 份各复评 3 次，共 20 次判定。语料 `eval/calib/`，统计 `python eval/calib/score.py`，
完整记录 `evaluator/CALIBRATION.md`。

**设计上的关键改动**：不做「正例 vs 反例平均分」的模糊比较——反例只违反一条结构规则，
内容本身可能是合格的，平均分本来就该接近。改成**按 rubric 已写明的判据给每份反例定一个
具体维度的期望值**（例如「不可逆对外动作没写影响范围 → 求极致 0 分，不给部分分」），
测的是 critic 有没有执行它自己写下的 rubric。

**结果：两个门槛都没过。**

| 指标 | 实测 | 门槛 | 判定 |
|---|---|---|---|
| 反例定向命中率 | 3/6 = 50% | ≥60% | 未过 |
| 正例全维达标率 | 2/6 = 33% | — | 未过 |
| 静默降级假阳性 | 2/6 = 33% | — | 未过 |
| 分数稳定率 | 4/4 = 100% | ≥70% | 过 |
| 结论稳定率 | 2/4 = 50% | — | 未过 |

**最刺眼的一条：verdict 区分度为零。** bench 的 6 份正例（`vh selftest` 必须全过的合格
样本）**没有一份被判「可交付」**：4 份需返工、2 份不可交付；反例同样 0 份可交付。
lint 说合格、critic 说全部返工，两个判定器在同一批文件上完全相反。

**三个病灶**（详见 `evaluator/CALIBRATION.md`）：

1. **2 分是默认值。** 2 分定义「有实质内容但存在可改进的空隙」，「可改进的空隙」对任何
   像样文档都成立，所以任何文档都会落到 2 分。校准集 12 份全在 2 分附近，r3 的 36 份里
   32/36 第一性是 2 分。
2. **verdict 与分数脱钩。** `critic.md` 只写了「silent_downgrade → 不可交付」一条映射，
   其余全靠自由裁量。实测同一份 `pre_deliver-nonrd-pricing` 三次评分 2/2/2、1/2/2、2/3/2，
   结论在「需返工 / 需返工 / 可交付」之间摆动，与分数无单调关系。
3. **静默降级没有操作定义。** 「降级」没词表、「取舍声明」没格式要求。结果在 bench 上
   6 份正例有 2 份被判 true（33% 假阳性），在 r3 的 36 份上零份判 true。同一套 prompt，
   两个语料上假阳性率从 33% 掉到 0%，不是阈值严宽问题，是判定标准不存在。

**对 r3 的影响**：`eval/RESULTS.md` 里所有 critic 分数（BASE 6.00 / OPEN 6.58 / BLIND 6.50）
都建立在这版 critic 上，既然它分不开正例反例，那些差异不能解释为「harness 的效果」。
**但 r3 的过程指标不受影响**——门禁首次通过率、返工份数、规则触发分布都是确定性的。

**下一步**：critic v2 三条改动（2 分拆成可数事实 / verdict 改确定性映射 / 静默降级给词表
和格式），改完重跑本校准，门槛反例定向 ≥80%、正例全维 ≥80%、verdict 区分度 >0。
过不了就再改，**不能调门槛**——调门槛等于承认尺子坏了还硬用。

### B3b · critic v2 重写与复校（已完成，通过）

**改了什么**（`evaluator/critic.md`）：

1. **分数由数出来的通过项换算**——每维 4 个检查项，4 过→3 分、3 过→2 分、2 过→1 分、
   ≤1 过→0 分。另加封顶规则（E3 不可逆动作无影响范围 → 求极致直接 0），否则只违反一项的
   反例也会拿到 2 分，校准立刻退回 v1 水平。
2. **verdict 改确定性映射**——`silent_downgrade` → 不可交付；任一适用维 0 → 不可交付；
   任一适用维 1 → 需返工；全部 ≥2 → 可交付。critic 不再自由裁量结论。
3. **静默降级给词表和格式**——降级词表 + 取舍声明三要素（放弃对象 / 因为 / 可接受前提），
   缺一即判 true。
4. **加产出类型适用性**（首轮复校暴露的缺口）——v2 第一次跑完全部判「不可交付」，
   共成长全线 0 分，连正例也是。根因不是分档，是 critic 拿复盘的标准去评任务拆解卡。
   改成先判类型（拆解卡 / 交付稿 / 沉淀记录）再定适用维度，不适用记 `null` 且不参与判定。

**复校结果**：

| 指标 | v1 | v2.1 | 门槛 |
|---|---|---|---|
| 反例定向命中率 | 3/6 = 50% | **6/6 = 100%** | ≥80% |
| 正例全维达标率 | 2/6 = 33% | **6/6 = 100%** | ≥80% |
| 静默降级假阳性 | 2/6 = 33% | **0/6** | — |
| 分数稳定率 | 4/4 | **4/4** | ≥70% |
| 结论稳定率 | 2/4 = 50% | **3/4 = 75%** | — |
| verdict 区分度 | 正例 0/6、反例 0/6 | **正例 6/6、反例 0/6** | >0 |

**三条残余问题**（写进 `evaluator/CALIBRATION.md`）：`pre_task-rd-hedge` 三次里有一次判错
（F4「承重句」仍是裁量项）；100% 只代表判得一致、不代表判得准，结构齐全实质空洞的产出
仍能拿高分——这个只能靠 B4 量化；校准集是作者自己写的正例，存在确认偏差。

### B5 · skipped 归因视图（已完成）

**问题**：`skipped` 字段已落盘，但 `report` 还没用它。一条规则零失败有两种可能：
太松（永远通过）或太窄（永远不触发）。不区分这两者，就没法判断该加强还是该扩触发词。

**已改**：`vhcore/telemetry.py` 新增 `_rule_health()`，`report()` 增加 `rule_health` 字段，
`vh report` 打印规则健康表：`规则 / 级别 / 触发 / 失败 / 跳过 / 失败率`。
从未触发的规则排最前，失败率显示"从未触发"而不是 0%。

**判读**：触发 0 次 = 形同虚设，要么扩触发词要么删；触发 >0 且失败率 0 = 在起作用但
没有挑战性；失败率 >50% = 要么规则过严要么产出确实差。

**验证**：用 3 条构造记录实测，`fp.real-goal`（触发 0 / 跳过 1）正确显示"从未触发"，
`cg.*` 三条（未跑 post_task）全部落在未触发区，`ex.redteam`（触发 2 / 失败 1）
显示 50%。排序与归因都符合预期。

## 备选方案

- **方案 B：不补 trial 语义，直接跑新实验，用"最终通过率"一个数。** 好处是今天就能
  开跑；代价是返工成本彻底不可见，而返工是 harness 最主要的副作用——同一批产出的
  「首次通过率」与「最终通过率」差多少，就是返工造成的，用单一口径会把这个问题
  永久藏起来。否决理由：口径错了，跑得越快错得越远。
- **方案 C：引入 Inspect 或 promptfoo 重写判定层，白拿校准与可视化。** 好处是不用
  自己实现一致性检验；代价是丢掉"零依赖、可离线、进 CI"三个现有优势，且要把 14 条
  规则翻译成它们的 DSL。否决理由：判定层不是瓶颈，指标口径才是；换框架解决不了
  "没有金标准"这个根本问题。
- **方案 D：先只跑 B2，把数字拿到手，方法学以后再说。** 好处是 README 能尽快有数字；
  代价是新数字仍然不可复现，三个月后同样的问题会重演一次，而且那次会以为自己是
  第一次遇到。否决理由：这正是把「跑得出」当成「跑得对」的失败路径，重复一次
  没有信息增量。

## 红队自查

- **如果三个口径跑出来长期完全相等**，说明返工根本没发生，A1 就是为一个不存在的
  现象增加复杂度。这个假设在跑够 20 个真实任务前无法验证，一旦发现两口径总是相等，
  应当把返工口径降级成 `--verbose` 里的附注。
- **如果 B1 补完反例后发现 `cg.tradeoff-declared` 与 `arb.no-silent-downgrade`
  拦的是同一批产出**，说明两条规则冗余，真正的规则数是 13 不是 14。删规则会与
  "规则越多越严谨"的直觉冲突，执行时会被本能抗拒。
- **如果 B2 跑完，求极致不再是提升最大的那项**，README 里「求极致提升最大」这个核心
  叙事就要改。这是新场景与旧场景的真实差异，不是 bug，但会让人怀疑整个 harness 的
  有效性。
- **如果 B3 校准跑出命中率低于 60%**，等于承认过去所有 critic 分数都不可用，
  包括所有已经写进 README 的分数。这个后果会直接推翻项目的对外叙事，届时正确的
  做法是重写结论而不是调低门槛。
- **如果 B4 的 4 份对抗样本全部逃逸**，说明这套确定性检查器的上限就是"防手滑"，
  所有关于"价值观被强制执行"的说法都要降级为"价值观被提醒"。这个降级不可逆，
  一旦公开就很难收回。

## 影响范围

**谁能看到**：只影响本仓库。`vhcore/telemetry.py` 与 `vhcore/cli.py` 的改动会改变
`vh report` 的输出格式，任何依赖旧格式解析的脚本会失效——当前没有这类脚本。

**能否撤回**：可以。A1/A2 是纯增量字段与新增函数，`git revert` 即恢复；
`report` 的旧输出字段（`by_stage` 的 `pass_rate`）全部保留，只新增不改写。
B1 是新增一个文件加一条 case，删掉即恢复。

**最坏后果**：如果 `record()` 的 `_next_trial()` 在并发写入时算错序号，返工统计会
整体失真。这个后果不可逆——错误的 trial 号写进归档后，无法从产出文件反推当时是
第几次尝试。

**补救方式**：`_next_trial()` 读的是追加前的完整文件，单进程使用下序号单调递增。
并发场景（多个 agent 同时 lint）会重复计数，因此 `eval/telemetry/` 的归档必须由
单次 `export` 生成，不能多个进程同时 export 同一个目标路径。

## 数据来源

## 技术债

- **`_next_trial()` 每次 record 重读整个 jsonl。** 为什么现在不还：当前记录数为个位数，
  重读成本可忽略。什么时候还：单文件超过 2000 条时改成维护 `.vh/trial.idx` 计数文件。
- **`_ephemeral()` 用路径前缀匹配判断临时目录**，容器或非标准 TMPDIR 下会漏判。
  为什么现在不还：当前只在 macOS 本地使用。什么时候还：第一次在 CI 或容器里跑出
  脏归档时。
- **B3 的人工标注集由我自己标**，等于让作者给自己的 rubric 打分，存在确认偏差。
  为什么现在不还：目前只有一个人维护这个项目。什么时候还：出现第二个使用者时，
  标注必须换人做。
