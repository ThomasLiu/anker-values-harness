# 搜索算法岗 · 40 人触达方案（交付稿）

> 目标：把首次触达回复率从 12%（约 5 人）提到 ≥25%（≥10 人），且不牺牲对话质量。

---

## 一、结论先行

12% 不是文案写得不够漂亮，是**这 40 个人收到消息的那一刻，判断的不是「这个岗好不好」，而是「这条消息是不是专门给我的」**。

绝大多数触达文案的结构是：自我介绍 → 岗位名称 → 薪资 → 要不要聊。这个结构里 100% 的内容在讲「我和我的岗」，0% 在讲「你」。被动候选人每天收 3-5 条这种消息，识别成本极低，直接划走。

所以这套方案只做三件事，其他都不做：

1. **首句不讲岗，讲他**。第一句话必须让他确认「这个人看过我的东西」。
2. **第二句给一个「跳跃」而不是「平移」**。推荐转搜索，如果只是「都是排序」，他为什么要动？必须说清搜索多给他什么、少给他什么。
3. **CTA 降到最低门槛**。不问「方便电话吗」，只要求回一个字。

---

## 二、12% 的归因（先说清楚我不确定什么）

回复率 = 送达率 × 打开率 × 「与我相关」判定 × 回复意愿。

| 环节 | 上一批可能的失分点 | 本次怎么改 |
|---|---|---|
| 打开 | 首句是「你好，我是 XX 的猎头」 | 首句换成他的技术方向 |
| 与我相关 | 通篇讲岗位，没有一句关于他 | 每条至少一个只属于他的技术锚点 |
| 回复意愿 | 要求电话沟通，成本高 | 回一个字 / 回「不」即可 |
| 送达 | 渠道混杂，可能重复触达 | 40 人先去重，单一渠道首发 |

**必须说清的不确定性**：12% 里有多少是「文案问题」、多少是「名单问题」，现在没有数据能分开。如果 40 人里有 20 人根本不认搜索方向，文案改到天上去也只能救另外 20 人。所以本方案在判据里设了一条兜底：7 天后整体 <15%，先查名单，不许只改文案再发一轮。

---

## 三、文案（三条，可直接复制发送）

三条对应三个切入角度，**首句各不相同、均不含薪资**。按候选人背景分派（分派规则见第五节）。

### A 版｜能力增量（适合：做召回 / 粗排，模型迭代经验明确）

```
你做召回的话，双塔加 ANN 那套应该很熟了。

我这边一个搜索的坑不一样：query 是用户自己打的，意图是明的，难在 200ms 里把纠错、改写、类目预测串完——这块推荐里基本碰不到。

想聊吗？回「1」我先把 JD 发你。
```

正文 98 字。为什么这么写：做召回的人最熟的是「用行为猜意图」，搜索把「猜」这一步去掉了，换成了「在极短时间内解析一个明确的、但写得很烂的意图」。这是能力增量，不是平级跳槽。

### B 版｜反馈闭环（适合：做精排 / 多目标，在意模型对业务指标的真实影响）

```
你做精排多目标，最烦的应该是离线 AUC 涨了、线上 GMV 不动。

搜索链路短：query 到成交只隔一层排序，一个改动两三天就能在 GMV 上看见，不用等一个月。

有兴趣回「搜」，我把团队在攻的两个问题发你。
```

正文 92 字。为什么这么写：3-5 年的精排工程师最大的挫败感来自「离线指标和线上收益脱节」。搜索的链路短，验证周期短，这是可以直接兑现的诱惑，不需要画饼。

### C 版｜成长天花板（适合：同一方向做满 3 年以上、简历上没有明显职责扩展）

```
你在推荐做了三四年，模型这块应该到瓶颈了：再往上要么转管理，要么换一个更难的问题。

搜索是后者。query 理解没有标准答案，一个类目预测错，整条链路都歪。这个岗是从「调模型」往「定义问题」走。

不想聊回个「不」，我不打扰。
```

正文 96 字。为什么这么写：这批人真正焦虑的不是钱，是「再做三年还是调模型」。C 版不承诺钱，承诺问题的难度。

**注意 C 版的 CTA 是「回个不」**。这是故意的：把拒绝的成本也降到最低，能拿到「明确拒绝」这个数据点，比沉默有用。但**「不」不计入回复率**，统计时必须单列（见第七节）。

---

## 四、把「技术锚点」升级成「看过你」（强烈建议做，但不是必须）

上面三条的个性化只到「技术方向」这一层——它能证明「我懂你这行」，但不能证明「我看过你这份简历」。差一档。

如果时间允许（40 份简历，每份 4-5 分钟，约 3 小时），把首句换成简历里的一句原话。取句公式：

> **首句 = 他简历里最具体的一个技术动作 + 一个该动作必然伴随的坑**

四个成句示范（按简历信号直接取用）：

- 简历出现「向量召回 / 双塔 / ANN 索引」→ 「你把召回从双塔换到多路那阵子，冷启动那批 item 的召回率应该掉得挺难看。」
- 简历出现「DIN / DIEN / 序列建模」→ 「你做过用户行为序列建模，那长序列截断到多少这一步，你们当时是怎么定的？」
- 简历出现「多目标 / MMOE / 样本权重」→ 「你做多目标的时候，CTR 和 CVR 那两个塔的梯度打架，最后是靠 loss 权重压下去的还是靠样本重采样的？」
- 简历出现「特征工程 / 实时特征 / Flink」→ 「你搞实时特征那套，样本穿越这个坑应该踩过——线上和离线对不上的时候你们怎么定位的？」

这四句的共同点：**都指向一个他一定踩过的具体坑**。人对自己踩过的坑有本能的表达欲，这是回复率最便宜的来源。

---

## 五、分组与发送节奏

### 分组（40 人）

先按「简历是否出现 search / query / 排序 / 召回」做一次二分（有 = 高匹配，无 = 低匹配），**在每一层内部随机分 A/B/C 三组**，保证三组的匹配度分布一致，否则比出来的差异是名单差异不是文案差异。

| 组 | 人数 | 文案 | 目的 |
|---|---|---|---|
| A | 13 | A 版 | 测「能力增量」角度 |
| B | 13 | B 版 | 测「反馈闭环」角度 |
| C | 14 | C 版 | 测「成长天花板」角度 |

### 节奏

- **T+0**：首触。工作日上午 10:00-11:00 或晚上 20:30-21:30 发。理由：这两段是被动候选人刷手机、且不在会议里的时间。
- **T+3**：只对「未读 + 已读未回」发一次跟进，**必须带新信息，不能催**。
- **T+7**：收尾，给退出选项 + 一个反问。

### T+3 跟进话术（可直接用）

```
补一条上次没说的：这个岗不是新设的坑，是原来的人转管理空出来的，HC 已经批了。

你要是暂时不动也没关系，我下季度还有类似的再找你。
```

### T+7 收尾话术（可直接用）

```
最后一条，不打扰了。哪天想看机会，直接搜我名字就行。

另外问一句：这次没回，是方向不对还是时候不对？回一个字我就知道了，对我下次找人有用。
```

### 已读不回（24 小时后单独发，仅一次）

```
看到你读了，估计在忙。

就一句话：这个岗最难的是 query 理解，不是排序模型。如果你现在做的推荐已经让你觉得没新东西了，这个可能值得看一眼。

不方便回也没事。
```

## 六、渠道与时机

| 渠道 | 用不用 | 理由 |
|---|---|---|
| 脉脉 | 首选 | 被动候选人在这里有活跃的职场身份，且私信不折叠 |
| 领英 | 次选 | 覆盖外企背景，但国内电商算法人群密度低 |
| 微信 | 仅对已建立联系的人 | 冷加微信通过率低，且失败一次就没有第二次 |
| Boss 直聘 | 不用 | 平台上的人以主动求职为主，与「被动候选人」这个前提冲突，混用会污染数据 |

**40 人发送前必须去重**：同一人跨渠道只发一次。重复触达是这个人群最反感的事，一次重复就能让整批口碑崩掉。

---

## 七、数据回收表

每天记一行，7 天后按组汇总。

| 字段 | 说明 |
|---|---|
| 候选人 ID | 脱敏编号 |
| 分组 | A / B / C |
| 匹配层级 | 高 / 低 |
| 发送时间 | 精确到小时 |
| 状态 | 未读 / 已读 / 回复 / 明确拒绝 / 拉黑 |
| 回复内容摘要 | 一句话 |
| 回复用时 | 小时 |

**统计口径（必须提前定死，否则数据没法比）**：
- 回复率 = 有效回复人数 ÷ 该组发送人数。**「明确拒绝」和「回个不」不算有效回复，单列一栏。**
- 分母只算成功送达的（被拉黑、账号不存在的不算）。

---

## 八、发送前 checklist（逐条打勾才发）

- [ ] 40 人已去重，无跨渠道重复
- [ ] 每条首句不含薪资数字
- [ ] 每条正文 ≤120 字
- [ ] 每条至少一个只属于他的技术锚点，无「您很优秀」「看机会吗」这类可套用句
- [ ] 全文零占位符（无方括号、无 XX、无某某）
- [ ] 所有硬信息（团队规模、汇报线、HC 数）已由客户书面确认
- [ ] 薪资只写区间，不写具体档位
- [ ] 三条文案首句互不相同

---

## 关键假设

- 假设：这批人至少 60% 有搜索 / 排序 / 召回相关经验，不是纯推荐业务工程 → 验证：发送前逐份按关键词打标统计占比，低于 60% 停止发送、先重筛名单。
- 假设：12% 的口径是「7 天内唯一回复人数 ÷ 送达数」→ 验证：调上一批发送记录核对分母是否含重复触达，口径不一致则 12% 不可比，本次重新设基线。
- 假设：这批人是被动求职，对陌生消息默认忽略 → 验证：抽 5 份简历看最近入职时间，12 个月内入职占比超过一半则说明多数人刚跳完槽，触达价值本身低。
- 假设：60-80 万对 3-5 年推荐算法工程师是「有吸引力但不稀缺」，撑不起单独作为回复理由 → 验证：向客户要近 6 个月同岗位 3 个成交 offer 的实际数字，若集中在下沿则文案不得把薪资当主钩子。
- 假设：主渠道私信首条可见字数约 200 字，超过会被折叠 → 验证：发送前用自己账号在目标渠道各发一条测试消息，确认截断位置。
- 假设：「回个不」的接受度高于沉默，能把拒绝显性化 → 验证：C 组统计「明确拒绝」占比，若超过 30% 说明 C 版语气过重，下一轮降调。

## 备选方案

- **备选 1：薪资前置型**——首句直接「60-80 万，搜索算法，看机会吗」。不选，因为 3-5 年推荐工程师对这个区间本来就有预期，薪资是必要条件不是理由；前置薪资会把对话变成比价，对方现薪一旦接近上限就直接出局。这也违反了「首句不含薪资」这条自定判据。
- **备选 2：完整 JD 长文型**——把岗位描述完整发过去。不选，因为触达是打断场景不是阅读场景，超过 200 字会被折叠；而且长文会被一眼判定为群发，反而降低回复意愿。
- **备选 3：共同联系人背书型**——找内推人或共同好友转发。**这个其实是三个里最优的**，信任从人传到人，回复率通常明显高于冷触达。不选的原因不是它不好，是我拿不到这 40 人的社交图谱，且需要客户配合，7 天窗口内做不到。已登记进技术债。
- **备选 4：电话 / 语音优先**——不选，被动候选人接陌生电话意愿低，且 40 人无法并行，单位时间产出最差。

## 红队自查

1. **12% 可能根本不是文案问题，我可能在整个方案上归错了因。** 如果 40 人里只有 20 人真的匹配搜索岗，剩下 20 人写什么都白写。这时候把目标定在 25%，本质是把名单问题包装成文案问题——方案看起来有效，实际只是把分母换掉了。如果我错，最可能是错在这里。
2. **「技术锚点」开场比「公司名 + 项目名」弱一档，这是硬伤。** 它证明「我懂这行」，但不证明「我看过你」。真正的个性化要逐份读简历，40 份约 3 小时。如果执行的人不做这一步，这套文案会退化成模板，回复率不会比 12% 高多少。这是执行风险，我改文案解决不了。
3. **「推荐转搜索是升级」这个叙事，对一部分人是劝退。** 搜索迭代慢、数据量级小于推荐、坑位更少。我选择在 C 版里说真话（承认要换更难的问题），这会筛掉一批只想安稳的人。如果客户的 KPI 只有回复率，我这个选择是错的——它提高质量、压低数量。
4. **25% 这个目标，在 40 人样本上 7 天内可能根本验证不了。** 25% 是 10 人，随机波动 ±3 人很正常，A/B/C 三组各 13 人，组间差异大概率被噪声淹没。也就是说我承诺了一个统计上分辨不出的实验，最后只能说「整体比 12% 好」，说不出「哪条文案更好」。
5. **「回个不」会让回复率虚高。** 我在口径里把明确拒绝单列了，但如果客户自己拉数据、把「不」算进回复，报出来的数字会比真实有效对话多。这个风险我只能提示，控制不了。

## 影响范围

- **谁会看到**：40 个外部候选人；可能被截图转发给他们的同事、其他猎头、以及候选人所在公司的 HR。文案里任何关于岗位的硬信息（团队规模、汇报线、HC 数、薪资区间）一旦发出，就代表客户公司对外的正式口径。
- **能否撤回**：不能。私信发出即达，撤回会二次打扰且更显不专业。所以这 40 条是不可逆动作，发送前的 checklist 是唯一的闸门。
- **最坏后果**：
  1. 岗位信息与实际不符（比如 HC 其实没批、汇报线不是我以为的），候选人入职后落差大，客户在候选人圈的口碑受损，且损伤会通过脉脉扩散。
  2. 同一候选人在脉脉和微信被重复触达，被判定为骚扰，直接被拉黑，这个人永久失去。
  3. 薪资区间被截图外传，影响客户薪酬体系的保密性。
  4. 三条文案同时发，如果语气都偏硬，可能触发平台的风控（脉脉对高频私信有限制），导致账号受限，后续所有触达都发不出去。
- **补救方式**：
  1. 所有硬信息发前必须客户书面确认，我不编任何一个数字。
  2. 发送前用「姓名 + 手机号」做一次 40 人去重，跨渠道只发一次。
  3. 薪资只写区间不写档位，且不在首条出现。
  4. 分三天发完（每天 13-14 条），避免触发平台风控；出问题可立即停。

## 技术债

- **欠了什么**：
  1. 个性化只做到「技术方向」级，没做到「公司 + 项目」级。
  2. 没有使用共同联系人背书（这是四个方案里最优的那个）。
  3. 只做了文案 A/B/C 对照，没做渠道对照，渠道变量未控制。
- **为什么现在不还**：
  1. 需要逐份读 40 份简历约 3 小时，且我现在没有简历访问权。
  2. 社交图谱数据我没有，需要客户提供内推人名单。
  3. 7 天窗口内多开一个变量，归因会彻底失效。
- **什么时候还**：
  1. 下一批（r2）把「读简历取首句」写进发送前 SOP，作为硬性检查项，不读完不发。
  2. r2 之前向客户要内推人名单，对高匹配层优先走背书路径。
  3. r2 用同一套文案换渠道做对照，把渠道变量单独测出来。

## 取舍声明

- 取舍声明：为了在 7 天内拿到可归因的对照数据，放弃了「40 人一次性全发完」的覆盖速度，因为不分组的全量发送无法区分是文案起作用还是名单本来就好。代价是整体回复人数晚 7 天才能看全，这个牺牲可接受——这批人不是一次性的，7 天的等待换一个能复用的结论。
- 取舍声明：为了文案能立刻发送、不依赖逐份读简历，放弃了「公司名 + 项目名」级的个性化，只做到「技术方向」级。因为 40 份简历 3 小时的阅读成本在本次窗口内无法保证执行，写一个执行不了的方案等于没写。这个牺牲不完全可接受——它会损失一部分回复率，已在技术债登记，r2 必须补上。
- 取舍声明：为了不误导候选人，放弃了「搜索比推荐更好」的包装，在 C 版里承认搜索迭代更慢、坑位更少。因为候选人入职后一定会发现这件事，前期隐瞒换来的是入职即离职。这个牺牲可接受，但它会压低回复率、提高匹配质量，如果客户只看回复率这个指标，需要提前对齐预期。

---

**一句话总结**：这套方案能提高的是「愿意看的人」的回复率，不能提高「本来就不该发的人」的回复率。如果 7 天后只有 15%，问题在名单，不在文案。
