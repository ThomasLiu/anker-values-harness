# 任务拆解卡：A 客户第 N 周招聘进展周报

## 表面需求

周五给 A 客户 HRD 发一封周报，汇报本周数据：推 6 人、2 人进面试、1 人被拒（嫌薪资低）、3 人待反馈。

## 真实目标

- 表面需求：一封把 6/2/1/3 四个数字讲清楚的周报。
- 我判断的真实目标：在客户已经公开质疑「你们推的人质量不行」的前提下，用这一周**可核对的事实**把「质量」从客户的**感觉**拉回到**证据**，并让客户在读完这封邮件后对两件事做出决定——(a) 是否调整该岗位的薪资带宽；(b) 3 个待反馈的候选人什么时候给结论。
- 依据有三条：
  1. 上周的投诉词是「质量」，但本周唯一有明确原因的负结果是「薪资」，不是「能力」。如果周报只是罗列数字，客户会把它读成「又一次证明质量不行」；如果把薪资这一条讲透，它是本周唯一能反转质量判断的证据。
  2. 3 个「待反馈」意味着客户侧有 3 个判断压着没做。这 3 个判断不做出来，下周漏斗只会更难看，而我们无法单方面推动。
  3. 这两件事都不是「多写点字」能解决的，必须让客户动手。所以周报的成败标准不是「信息完整」，而是「客户读完做了哪个决定」。

## 硬约束

- 时间：本周五 18:00 前发出，过时这封邮件就失去意义（客户按周节奏看）。
- 收件人：A 客户 HRD；可能被转发给其招聘负责人，因此措辞要经得起二次阅读。
- 合规：不得出现候选人真实姓名（用岗位 + 编号代称），不得出现其他客户名称或对比数据。
- 数据：口径以 ATS 为准，不修饰、不四舍五入到「好看」。
- 不做：不承诺「下周一定补足 N 人」这类我无法控制的数字。

## 关键假设

- 假设：「1 个被拒（嫌薪资低）」是**候选人拒绝了客户给出的薪资**，而不是客户嫌候选人要价过高。这两种情况的结论完全相反，写错方向会当场翻车。
  → 验证：调该候选人的期望薪资记录，与客户岗位 JD 的薪资带宽做数值对比；同时找 AM 确认客户 HR 反馈的原话，确认拒绝方向。
- 假设：3 个「待反馈」是**客户侧尚未给出面试结论**，不是候选人没回面试邀约。
  → 验证：查 ATS 中这 3 人的状态字段与最近一次跟进时间戳；若状态停在「已推荐/已约面」且最后动作方是客户，则判定为客户侧待办，邮件里必须点名列出。
- 假设：上周「质量不行」的抱怨，具体指向**简历与 JD 的匹配度**，而不是响应速度、沟通态度或人选到岗意愿。
  → 验证：调取上周客户的原话或会议纪要，逐句定位抱怨对象；如果实际指向响应速度，这封邮件的重点要整体改写。
- 假设：本周 6 人中至少有 4 人满足 JD 的硬性条件（学历/年限/必备技能）。
  → 验证：按 JD 硬性条件对 6 份简历逐条打分，算出硬性条件匹配率；匹配率低于 4/6 时，邮件里不能主动提「质量」二字，只能谈流程。
- 假设：客户当前薪资带宽低于该岗位在本地市场的实际成交区间，这是「被拒」的根因。
  → 验证：拉取我们近 6 个月同岗位、同城市的成单薪资中位数，与客户带宽上限对比，得出差额。

## 验收标准

- 邮件正文 ≤600 字，客户 HRD 3 分钟内能读完并知道下一步 → 判据：正文字数 ≤600，且不依赖任何附件才能理解结论。
- 漏斗数字与 ATS 完全一致且自洽：6 = 2 + 1 + 3 → 判据：四数相加校验通过，零口径差异；任一数字对不上即不通过。
- 对「1 被拒」必须给出归因，且归因落在薪资带宽上而不是候选人能力上 → 判据：该段必须出现具体薪资数字对比（候选人期望 vs 客户带宽上限），且差额可计算。
- 必须正面回应上周的质量投诉，但不得辩解 → 判据：全文出现「上周」相关表述 ≥1 处，且不出现「但是/其实/并非/并不是」开头的反驳句，人工复核通过。
- 下一步行动 ≤3 条，每条同时含责任方和日期 → 判据：条数 ≤3，每条都有明确责任方 + 具体日期，缺一即不通过。
- 零候选人真实姓名、零其他客户名 → 判据：交付前关键词自查，命中数为 0。
- 全文不出现「行业惯例/常规做法/大家都这样」作为论据 → 判据：命中数为 0，任何结论必须带数据或推理依据。

## 可逆性

这封邮件**对外发出后不可撤回**（可发更正邮件，但第一印象已形成）。最坏后果是客户把「薪资」解读成我们在为交付不力找借口，信任进一步下降。降低风险的方式：把薪资对比写成**共同面对的外部事实**（市场价 vs 带宽），而不是「所以不是我们的问题」。
