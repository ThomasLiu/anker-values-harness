# 任务拆解卡：8 位候选人优先级排序

## 真实目标

**表面需求**：把 8 个候选人排个优先级，告诉我先推谁。

**我判断的真实目标**：客户要的不是一个排名列表，而是**一次面试资源的分配决策**——他手里只有有限的面试官时间，需要知道「这周先约谁、约几个、哪些可以直接放掉」。排名只是这个决策的表达形式。

**依据**：
1. 客户说「告诉我先推谁」，而不是「给我一份评估报告」——他要的是行动指令，不是分析。
2. 客户把 JD 写得极简（4 条硬指标，无业务背景、无团队现状、无薪资带宽），说明他默认我理解这类岗位，希望我**替他承担判断**，而不是把问题退回给他。
3. 客户说「信息我稍后给」但本次并未给——意味着他期待我先建立判断框架，这本身就是他要的交付物之一。

**由此推导的交付形态**：一个「首推 1 人 + 备选 2 人 + 明确淘汰名单」的三档结构，外加一张风险敞口表，而不是 1-8 名的扁平排名。扁平排名无法指导行动。

## 关键假设

- 假设：JD 的「5 年以上 Go」是硬门槛，客户不会为其他项超配但 Go 不足的人破例 → 验证：交付时单列「擦边候选人」并附一句「若 5 年是优选而非硬卡，C 应升至第 2 位」，让客户用一句话推翻，成本最低。
- 假设：「高并发交易系统」指撮合、清结算、风控这类有状态、强一致的金融链路，而不是泛指任何高 QPS 的互联网业务 → 验证：首轮面试让候选人描述一次「数据不一致事故」的排查过程，能讲清事务边界与对账机制的才算真做过交易系统。
- 假设：候选人简历里的 QPS、延迟、团队规模数字存在系统性夸大（通常虚高 1 个数量级）→ 验证：面试时追问压测方法、机器规格、单机还是集群、P99 还是均值，四个问题里答不出两个即判定数字不可信。
- 假设：客户团队当前处于「已有系统要提质」而非「从 0 搭建」阶段 → 验证：向客户直接确认一句「现在最痛的是稳定性还是从零建」，这决定我该推「深度优化型」还是「从 0 到 1 型」的人。
- 假设：「带过 3 人以上小组」客户在意的是技术带队（tech lead）而非行政管理 → 验证：面试问「你带的人里有没有被你否掉的技术方案，为什么」，能讲出具体冲突的才算带过队。
- 假设：本科以上是 HR 侧合规硬卡，技术侧可议 → 验证：交付时标注哪些人卡在学历上，由客户向 HR 确认，不由我替他决定。

## 验收标准

- 8 位候选人必须全部出现在最终名单中，位次 = 1..8 且互不相同，并列数 = 0、遗漏数 = 0。
- 每位候选人给出 4 条 JD 硬指标的逐项判定（满足 / 擦边 / 不满足），每条判定必须引用其具体经历数字，不允许只写「经验丰富」。
- 首推人选明确到 1 人，且给出「为什么是他而不是第 2 名」的对比理由，至少 1 条可验证的差异点。
- 至少标出 3 个信息缺口，并给出对应的补问清单（问什么、问谁能证伪）。
- 排序依据必须来自事先定义的评分维度，维度权重在见到候选人之前写定，不允许看到人之后再调权重。
- 交付中含至少 2 个备选排序方案（如「硬门槛优先」与「潜力优先」），并说明在什么条件下切换到备选方案。
- 必须列出 ≥3 条本次交付**不能**回答的问题（如候选人薪资期望、到岗时间、稳定性风险），避免客户误用结论。
