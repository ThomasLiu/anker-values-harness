# gate: 任务前（pre_task）

> 规则的事实源是 [`values.toml`](../values.toml)。本文件不重复规则定义，只讲**怎么做得比 lint 要求更好**。
>
> 生成阶段 prompt：`vh prompt pre_task --task "……"`

## 这个 gate 在防什么

防的是**用解法冒充问题**。

用户说「帮我写个触达文案」，这是解法。真实问题可能是「这批候选人为什么回复率低」。如果直接开始写文案，写得再好也是在错误的问题上努力。

第一性在这里的具体含义：把需求拆到不能再拆，直到每一条都能被验证。

## 四个必答问题

**1. 表面需求是什么**
原话复述，不要加工。加工会丢掉信息。

**2. 我判断的真实目标是什么**
写你的判断和依据。判断错了没关系——写出来才能被纠正，藏在心里就永远是错的。

**3. 硬约束是什么**
时间、预算、合规、不可动的东西。区分「真约束」和「习惯」：真约束推翻不了，习惯可以。

**4. 关键假设是什么**
这是唯一会被 lint 强制检查的部分。标准是**可证伪**。

| 不合格的假设 | 为什么不行 | 合格的写法 |
|---|---|---|
| 客户应该想要更快的交付 | 「应该」不可证伪 | 客户在上一轮明确说过交付速度优先于价格 → 验证：翻上一轮邮件确认 |
| 候选人不太愿意换城市 | 模糊，无法验证 | 目标池 80% 在深圳有房 → 验证：抽样 10 份简历看现居地 |
| 这个岗位预算在 40-50 万 | 有数字但没来源 | 客户 JD 写 40-50 万，但 HR 口头说过可上浮 → 验证：找 HR 确认上浮空间 |

一条好假设长这样：

```
- 假设：客户对费率的敏感度低于对到岗速度的敏感度
  → 验证：调最近 3 单的成交记录，看是否出现过因费率丢单
```

## 验收标准的写法

标准必须在结果之前定。定晚了，标准会被结果倒推——这是人（和模型）的本能。

可判定的标准有三个特征：有数字、有二值判据、或者有明确的通过条件。

```
不合格：输出一份高质量的竞对分析
合格：  覆盖 5 家直接竞对；每家至少 3 个可验证事实（来源可追溯）；
        结论部分给出「我们应该打哪个差异点」的单一建议，不给选项清单
```

## 分层：不是所有任务都要跑全量

轻任务（改个措辞、查个数）用 `vh prompt pre_task --brief`，只注入 blocking 规则。
重任务（对外交付、影响决策）跑全量。

给每个任务都套全套 gate 的后果是 harness 被关掉——这是最常见的一种死法。

## 出口条件

```bash
vh lint pre_task <你的拆解卡>
```

exit 0 才能进下一步。
