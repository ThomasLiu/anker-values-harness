# gate: 交付前（pre_deliver）

> 规则的事实源是 [`values.toml`](../values.toml)。本文件只讲怎么做得更好。
>
> 生成阶段 prompt：`vh prompt pre_deliver --task "……"`

## 这个 gate 在防什么

防的是**把第一个想到的方案伪装成最优方案**。

「求极致」不是「再努力一点」，是「证明这个解在约束下是当前最好的」。证明需要对照物——没有备选方案就没有对照物。

## 备选方案不是凑数

lint 只数条数（≥2）。但凑数的备选方案比没有更糟，因为它制造了「我考虑过了」的假象。

一条真备选必须满足：**如果你老板选它，你能说出他为什么对**。

```
凑数：方案 B：用另一种方式做同样的事
真备选：方案 B：只做 Top 20 候选人的人工精筛，放弃全量覆盖
        —— 成本降 60%，代价是长尾候选人完全放弃。如果客户更在意成本而非覆盖率，这个方案更优。
```

## 红队自查怎么写才有用

lint 只要求 ≥3 条。但「沟通可能不及时」这种不叫弱点，叫免责声明。

判断标准：**这条弱点如果成立，方案会不会崩？** 会崩的才是弱点。

```
无效：可能存在信息不对称
有效：我把 40-50 万当成客户预算上限，依据只是 JD。如果实际预算是 35 万，
      整个候选人池要重筛，方案作废。这个假设我无法在交付前验证。
```

好红队自查有一个副作用：它经常直接产出「关键假设」里该写的东西。两个 gate 是通的。

## 惯例禁令怎么理解

不是禁止你知道行业惯例，是禁止你**用它当理由**。

```
违规：行业普遍按 25% 收费，所以我们建议 25%
合规：行业普遍按 25% 收费，但我们测算 22% 时毛利额最大（见附表），所以建议 22%
```

差别只在于后半句有没有。lint 查的就是这个：同一行里有没有「因为 / 依据 / 测算 / 数据」这类理由标记。

## 影响范围：价值观的边界

「顶着巨大风险」指的是做别人不敢做的判断，不是做没有退路的操作。

一旦产出涉及对外或不可逆动作（发布、群发、提交、删除、付款），必须写清四件事：

1. 谁会看到
2. 能不能撤回
3. 最坏后果是什么
4. 出事怎么补救

一个把「求极致」理解成「敢删库」的 agent 是危险的，不是极致的。

## 取舍声明

只要出现了「简化 / 跳过 / 暂不 / 降低 / 不做」这类词，就必须有一行：

```
取舍声明：为了 本周内交付可用的 v1 放弃了 全量候选人覆盖，因为 客户下周就要启动面试，
          长尾部分可以用第二轮补。这个牺牲可接受的前提是客户确认接受两轮。
```

注意后半句——**牺牲可接受的前提**。只写「为了 X 放弃 Y」是交代，写清前提才是负责。

## 出口条件

```bash
vh lint pre_deliver <交付稿>
```

exit 0 才能交付。被拦下就补，不要绕过——绕过一次，这套 harness 就废了。
